# 项目开发规范

## 适用范围
- 本文件适用于当前目录及其子目录。
- 开始修改前，先阅读相关代码和构建配置，沿用项目现有结构与实现方式。
- 修改应围绕当前任务展开，避免无关重构、格式化或依赖升级。
- 如果我没有明确要求的情况下，不得擅自修改 `AGENTS.md` 文件。

## 目录约定
- `tests/scripts/`：存放本地测试脚本和临时验证脚本。
- `tests/reports/`：存放测试报告、截图和测试日志。
- `tests/software/`：存放测试安装包、临时安装包和需要保留的历史安装包。
- `keys/`：存放本地签名密钥文件。
- 上述目录及其内容均不提交到 Git。
- 需要随代码维护的自动化测试，应放在项目约定的源码测试目录中，不放入上述本地测试目录。

## 开发环境
- 使用 Android SDK Platform 36 编译，`compileSdk` 设置为 36。
- `targetSdk` 和 `minSdk` 以项目配置为准，不因普通功能修改擅自调整。
- 使用项目提供的 Gradle Wrapper，JDK 版本应与项目构建配置兼容。
- 未经任务要求，不擅自升级 Gradle、Android Gradle Plugin 或其他依赖。
- 使用 BlueStacks 进行运行验证，并记录实际 Android 系统版本；模拟器系统版本与编译 SDK 版本分别记录。

## 修改要求
- 修改前确认相关功能的现有行为及影响范围。
- 遵循项目已有的代码风格、命名方式和架构约定。
- 涉及数据库、配置或持久化数据时，考虑旧版本数据的兼容性。
- 不覆盖或撤销用户已有的无关修改。
- 不将密钥、密码或其他敏感信息写入源码、测试脚本、报告或日志。

## 构建与签名
- 测试安装包和临时安装包统一存放在 `tests/software/`。
- APK 文件名格式为：`项目名_版本号_versionCode_构建时间.apk`，例如：`MyApp_1.0.0_100_20261027_143000.apk`
- 安装包文件名中的版本信息必须与 APK 内实际版本一致。
- 安装到 BlueStacks 的安装包必须使用项目正式签名。
- 沿用项目固定的 `applicationId`，不通过添加包名后缀生成并存的测试版本。
- 签名密钥从 `keys/` 或项目已约定的安全位置读取，密码从本地配置或环境变量读取。
- 不在命令输出、构建日志或报告中打印签名密码。
- 缺少签名配置时，说明缺失项和阻塞原因，不自行生成替代密钥或改用调试签名。

### 基本验证
- 功能修改后，应完成相关构建检查，并在 BlueStacks 中验证。
- 至少覆盖：本次修改的主要功能和关键异常场景，与修改直接相关的功能流程，应用安装、启动和主要入口的基本冒烟检查。
- 测试范围应与修改风险相匹配，不要求对无关功能进行全面回归。
- 仅修改文档且不影响应用行为时，可以不构建和运行应用，但应检查文档内容的准确性。

### 全新安装
- 普通功能验证默认采用全新安装：卸载旧版本，再安装新版本。
- 卸载前核对目标设备和 `applicationId`，仅操作当前项目的应用。
- 卸载会清空应用数据；如存在需要保留的数据，先处理数据保留问题。
- 测试完成后，BlueStacks 中仅保留当前项目需要验证的一个应用版本。

### 升级兼容性
- 涉及数据库、配置、持久化数据或升级逻辑时，额外进行覆盖升级测试。
- 先安装旧版本并准备代表性数据，再使用相同包名、相同签名且满足升级版本要求的新安装包覆盖安装。
- 检查已有数据是否保留、迁移是否正确，以及相关功能是否正常。
- 升级测试必须在卸载旧版本之前完成，避免丢失验证所需数据。

### 测试记录
- 测试报告存放在 `tests/reports/`，至少包含：
  - 测试版本及对应代码版本；如存在未提交修改，应注明。
  - 测试环境，包括 BlueStacks 版本和 Android 系统版本。
  - 安装方式：全新安装或覆盖升级。
  - 测试步骤、预期结果、实际结果和结论。
  - 未通过项、未验证项及原因。
- 截图和日志按需保存，避免记录敏感信息。
- 无法使用 BlueStacks、正式签名或其他必要环境时，应完成可执行的检查，并明确说明剩余验证项。
- 不得将构建成功描述为功能测试通过，也不得声称完成实际未执行的测试。

### 忽略规则
- 确保项目根目录的 `.gitignore` 排除：
  - `/tests/`
  - `/keys/`
  - 本地环境配置和包含签名凭据的文件。
  - 编译产物、缓存及临时文件。
- 忽略规则应结合项目结构编写，避免误排除需要维护的源码或构建配置。
- `.gitignore` 不会自动取消对已跟踪文件的跟踪；如发现上述文件已被跟踪，应说明情况并妥善处理。

### 提交要求
- 仅在用户明确要求时创建 commit 或推送代码。
- 提交前检查差异和暂存区，确保不包含：密钥、密码及其他敏感信息、测试报告、测试安装包和临时文件与当前任务无关的修改。
- 提交信息使用中文，格式为：`类型：简短说明`，常用类型包括：新增、修复、重构、测试、文档、构建。
- 不擅自修改历史提交或执行强制推送。

## 完成交付
- 完成后简要说明：修改了什么，以及对功能行为的影响，已执行的构建和测试及其结果，安装包和测试报告的路径（如有），尚未验证的内容、已知问题或阻塞原因。
