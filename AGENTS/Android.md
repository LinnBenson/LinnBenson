# 项目开发规范

## 适用范围
- 本文件适用于当前目录及其子目录。
- 开始修改前，先阅读相关代码和构建配置，沿用项目现有结构与实现方式。
- 修改应围绕当前任务展开，避免无关重构、格式化或依赖升级。
- 如果我没有明确要求的情况下，不得擅自修改 `AGENTS.md` 文件。

## 目录约定
- `test_data/scripts/`：存放本地测试脚本和临时验证脚本。
- `test_data/reports/`：存放测试报告、截图和测试日志。每次的报告按时间和版本目录进行区分，例如 `20261027/1.0.0_100/`，便于追溯和管理。
- `test_data/software/`：存放测试安装包、临时安装包和需要保留的历史安装包。历史安装包最多保留 5 个，超过数量的旧安装包应及时清理。
- `keys/`：存放本地签名密钥文件。
- 上述目录及其内容均不提交到 Git。
- 需要随代码维护的自动化测试，应放在项目约定的源码测试目录中，不放入上述本地测试目录。

## 开发环境
- 使用 Android SDK Platform 36 编译，`compileSdk` 设置为 36。
- `targetSdk` 和 `minSdk` 以项目配置为准，不因普通功能修改擅自调整。
- 使用项目提供的 Gradle Wrapper，JDK 版本应与项目构建配置兼容。
- 未经任务要求，不擅自升级 Gradle、Android Gradle Plugin 或其他依赖。
- 使用 BlueStacks 进行运行验证，并记录实际 Android 系统版本；模拟器系统版本与编译 SDK 版本分别记录。
- 界面开发使用 `React Native + JavaScript`，安卓原生部分使用 `Java` 或 `Kotlin`。
- UI 框架请使用 `HeroUI Native` 来构建界面，保持与项目整体风格和交互一致。

## 开发要求及代码规范

### 基本原则
- 优先保证代码清晰、正确、易维护，方便后续人工阅读、调试和修改。
- 遵循项目现有架构、目录结构和代码风格；新增约定时应保持一致。
- 使用满足当前需求的简单实现，不为尚未明确的需求引入复杂架构、通用框架或额外依赖。
- 修改应围绕当前任务展开，避免无关重构和大范围格式化。

### 目录结构与职责划分
- 按功能模块组织代码，模块内部按职责合理分层。
- 界面展示、业务逻辑、数据访问和平台能力应有清晰边界，避免集中在同一个类或文件中。
- 界面层负责展示状态和转发用户操作，不直接承担复杂业务规则、网络请求或数据库操作。
- 共享代码应具有明确用途，不将不相关的逻辑堆放在 `Utils`、`Common` 或 `Manager` 等泛化文件中。
- 新增文件应放在职责匹配的位置，不随意增加目录层级。

### 命名与代码组织
- 类、函数、变量和文件使用清晰、准确的名称，体现业务含义，避免无意义缩写和模糊命名。
- 同一业务概念使用统一术语，不在不同模块中混用多种名称。
- 函数应围绕一个明确职责展开；出现多项独立职责或重复逻辑时，再进行合理拆分。
- 优先使用提前返回等方式降低嵌套，避免复杂条件、多层分支和难以理解的表达式。
- 不机械地按行数拆分代码，也不为了减少行数牺牲可读性。
- 对具有业务含义的数字、字符串和配置项使用有意义的常量或类型，避免魔法值。

### 类型、状态与数据流
- 优先使用明确的类型表达业务含义，避免使用松散的数据结构或字符串约定代替清晰的数据模型。
- 明确区分界面状态、业务数据和外部接口数据；仅在职责或结构存在实际差异时拆分模型。
- 状态应有明确的归属和更新入口，避免多处维护同一份可变数据。
- 优先使用不可变数据和受限的可见性，仅暴露必要的接口。
- 避免通过全局可变变量传递业务状态或形成隐式依赖。

### 抽象与依赖
- 在存在实际复用需求或明确职责边界时进行抽象，避免为单一简单实现创建多层转发。
- 不要求每个类都配套接口；接口应服务于实现替换、外部依赖隔离或必要的测试。
- 引入新依赖前，优先检查项目现有能力和平台原生能力。
- 新依赖应有明确收益，并考虑维护成本、兼容性及对安装包体积的影响。

### 注释与文档
- 注释使用中文，重点解释设计原因、业务约束、边界条件和非直观行为，不重复描述代码表面含义。
- 对复杂业务规则、兼容性处理和必要的变通方案说明原因。
- 对跨模块接口和重要公共能力，按需说明用途、参数约束、返回结果及异常行为。
- 修改代码时同步更新相关注释和文档，删除过时说明。
- 不保留大段注释掉的旧代码；未完成事项应明确说明原因和待处理内容，避免留下无上下文的 TODO。

### 公共组件复用与对接
- 开发前先检查项目已有的公共组件、基础能力和相似功能，了解其接口、使用示例及适用范围，优先复用，避免重复实现。
- 通用界面元素（如按钮、输入框、弹窗、加载状态、空状态和错误提示）优先使用项目公共组件，保持样式与交互一致。
- 网络请求、数据存储、日志、权限处理等基础能力，应通过项目已有的统一入口调用，不另建平行实现。

#### 接口与职责
- 公共组件应职责明确，通过清晰的参数、状态和事件回调与业务代码对接。
- 参数命名、默认值、回调语义及调用方式应与项目现有约定一致。
- 明确必填参数、可选参数、输入约束和状态更新方式，避免调用方依赖组件内部实现。
- 公共界面组件不直接绑定具体页面、导航逻辑、网络接口或业务数据源；业务行为由调用方传入或通过项目已有机制对接。
- 组件内部管理局部交互状态，业务状态由明确的持有方管理，避免组件与调用方重复维护同一状态。

#### 扩展与兼容
- 现有组件不能满足需求时，先判断需求属于通用能力还是页面特有逻辑，再选择扩展组件、组合现有组件或在业务层适配。
- 不为单个页面向公共组件加入专属业务判断，也不通过大量布尔参数堆叠不同功能。
- 修改公共组件前检查现有调用位置，评估对其他页面和模块的影响。
- 优先保持接口兼容；必须调整接口时，同步更新所有受影响的调用方、示例和测试。
- 不复制公共组件后仅修改少量样式或行为，形成难以同步维护的多个版本。

### 多语言支持
- 即使未明确提出多语言需求，也应使用项目技术栈对应的国际化机制，完成基础配置，便于后续扩展。
- 未明确语言支持列表时，仅需提供简体中文（`zh-CN`）语言资源，并将其设为默认及回退语言，无需添加其他语言或语言切换入口。
- 用户可见的文案应统一通过语言资源管理，不在界面代码或业务逻辑中硬编码。
- 项目已有国际化方案时，应沿用现有方案，避免重复引入框架。

#### 样式与交互
- 公共组件统一使用项目的主题、颜色、字体、间距及形状等设计资源，避免内部硬编码造成风格偏差。
- 按组件用途处理加载、禁用、空数据、错误及重复点击等状态，并明确由组件还是调用方负责。
- 用户可见文案支持语言资源，不在公共组件中写死业务文案。
- 按需提供样式和内容扩展入口，避免调用方通过访问内部视图、覆盖私有实现等方式修改组件行为。
- 样式设计时应考虑宽窄屏适配，确保在不同屏幕尺寸和分辨率下的显示效果一致。并且对折叠屏设备，应保证折叠和展开状态下的界面布局合理，在不同状态下均能正常显示和操作。折叠屏展开时也能自动调整让界面内容充分利用屏幕空间。

#### 验证与使用说明
- 对接后在实际页面中验证数据传入、状态更新、事件回调和异常场景，不能仅以编译通过作为完成标准。
- 修改公共组件后，验证现有典型调用场景，避免修复一个页面却破坏其他页面。
- 新增或调整较复杂的公共组件时，提供简洁的使用示例，说明参数、状态归属和事件处理方式。
- 仅在职责明确或存在实际复用价值时提取公共组件，避免将所有页面代码机械地组件化。

### 错误处理与日志
- 对可预期的失败提供明确处理，区分正常空结果、输入错误和系统异常。
- 不吞掉异常，不用无意义的默认值掩盖失败，也不在缺少恢复措施时捕获宽泛异常。
- 错误提示应便于用户理解；诊断日志应包含定位问题所需的上下文，但不得泄露敏感信息。
- 沿用项目统一的日志机制，不遗留临时调试输出。

### Android 平台规范
- 遵循组件生命周期，正确管理协程、监听器和资源释放，避免内存泄漏及重复执行。
- 网络、数据库和其他耗时操作不得阻塞主线程。
- 不在长生命周期对象中持有 Activity、Fragment 或 View 的引用。
- 用户可见文案统一使用语言资源；颜色、主题和可复用样式沿用项目资源体系。
- 涉及权限、系统版本差异和进程重建时，应处理与当前功能相关的兼容性及状态恢复问题。

### 修改后的检查
- 清理本次修改产生的无用导入、变量、函数及临时调试代码。
- 检查命名、职责划分、边界条件和错误处理，确保新增代码与现有实现一致。
- 使用项目已有的格式化、静态检查及相关测试验证修改，不为简单修改额外搭建工具体系。
- 对关键业务规则、缺陷修复和复杂边界补充必要测试，优先验证可观察行为，避免测试仅重复实现细节。

## 修改要求
- 修改前确认相关功能的现有行为及影响范围。
- 遵循项目已有的代码风格、命名方式和架构约定。
- 涉及数据库、配置或持久化数据时，考虑旧版本数据的兼容性。
- 不覆盖或撤销用户已有的无关修改。
- 不将密钥、密码或其他敏感信息写入源码、测试脚本、报告或日志。

## 构建与签名
- 测试安装包和临时安装包统一存放在 `test_data/software/`。
- APK 文件名格式为：`项目名_版本号_versionCode_构建时间.apk`，例如：`MyApp_1.0.0_100_20261027_143000.apk`
- 安装包文件名中的版本信息必须与 APK 内实际版本一致。
- 安装到 BlueStacks 的安装包必须使用项目正式签名。
- 沿用项目固定的 `applicationId`，不通过添加包名后缀生成并存的测试版本。
- 签名密钥从 `keys/` 或项目已约定的安全位置读取，密码从本地配置或环境变量读取。
- 不在命令输出、构建日志或报告中打印签名密码。
- 缺少签名配置时，说明缺失项和阻塞原因，不自行生成替代密钥或改用调试签名。

### 基本验证
- 功能修改后，应完成相关构建检查，并在 BlueStacks 中验证。
- 至少覆盖：本次修改的主要功能和关键异常场景，与修改直接相关的功能流程，应用安装、启动和主要入口的基本冒烟检查。
- 测试范围应与修改风险相匹配，不要求对无关功能进行全面回归。
- 仅修改文档且不影响应用行为时，可以不构建和运行应用，但应检查文档内容的准确性。

### 全新安装
- 普通功能验证默认采用全新安装：卸载旧版本，再安装新版本。
- 卸载前核对目标设备和 `applicationId`，仅操作当前项目的应用。
- 卸载会清空应用数据；如存在需要保留的数据，先处理数据保留问题。
- 测试完成后，BlueStacks 中仅保留当前项目需要验证的一个应用版本。

### 升级兼容性
- 涉及数据库、配置、持久化数据或升级逻辑时，额外进行覆盖升级测试。
- 先安装旧版本并准备代表性数据，再使用相同包名、相同签名且满足升级版本要求的新安装包覆盖安装。
- 检查已有数据是否保留、迁移是否正确，以及相关功能是否正常。
- 升级测试必须在卸载旧版本之前完成，避免丢失验证所需数据。

### 测试记录
- 测试报告存放在 `test_data/reports/`，至少包含：
  - 测试版本及对应代码版本；如存在未提交修改，应注明。
  - 测试环境，包括 BlueStacks 版本和 Android 系统版本。
  - 安装方式：全新安装或覆盖升级。
  - 测试步骤、预期结果、实际结果和结论。
  - 未通过项、未验证项及原因。
- 截图和日志按需保存，避免记录敏感信息。
- 无法使用 BlueStacks、正式签名或其他必要环境时，应完成可执行的检查，并明确说明剩余验证项。
- 不得将构建成功描述为功能测试通过，也不得声称完成实际未执行的测试。

### 忽略规则
- 确保项目根目录的 `.gitignore` 排除：
  - `/test_data/`
  - `/keys/`
  - 本地环境配置和包含签名凭据的文件。
  - 编译产物、缓存及临时文件。
- 忽略规则应结合项目结构编写，避免误排除需要维护的源码或构建配置。
- `.gitignore` 不会自动取消对已跟踪文件的跟踪；如发现上述文件已被跟踪，应说明情况并妥善处理。

### 提交要求
- 仅在用户明确要求时创建 commit 或推送代码。
- 提交前检查差异和暂存区，确保不包含：密钥、密码及其他敏感信息、测试报告、测试安装包和临时文件与当前任务无关的修改。
- 提交信息使用中文，格式为：`类型：简短说明`，常用类型包括：新增、修复、重构、测试、文档、构建。
- 不擅自修改历史提交或执行强制推送。

## 完成交付
- 完成后简要说明：修改了什么，以及对功能行为的影响，已执行的构建和测试及其结果，安装包和测试报告的路径（如有），尚未验证的内容、已知问题或阻塞原因。
- 打包发布版本时，对外发布的文件及发布压缩包内的内容仅限以下三项：
  - `SHA256SUMS.txt`：两个正式签名 APK 的 SHA-256 校验文件。
  - `项目名-版本号-arm64-v8a.apk`：ARM 架构安装包。
  - `项目名-版本号-x86_64.apk`：x86 架构安装包。
- 发布说明和 `README.md` 应采用真实开发者面向用户的自然、简洁表述，避免明显的 AI 模板腔、套话、重复总结和不必要的说明。只写与功能、使用、安装、兼容性、已知问题及必要许可信息有关的内容；不要夹带 AI 工作过程、对话记录、任务汇报、工具调用、内部验证流水账或自我评价。发布说明直接说明本次新增、修复和用户需要注意的变化；README 聚焦项目介绍与实际使用。内容必须准确，不虚构开发经历或验证结果，不因精简而省略影响用户使用的重要限制。
